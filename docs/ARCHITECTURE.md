# Architecture

`crates/core` owns public state transitions and bill calculation. Every command runs against a clone, and only a successful result can replace durable state. Permissions, quantities, availability, session validity, order approval, item progress and cash settlement are enforced in Rust.

`src/engine.ts` is a small UTF-8 JSON bridge to the compiled WASM crate. It allocates and frees both buffers. `src/store.ts` serializes local changes in one IndexedDB update transaction; it rereads the authoritative latest state inside that transaction and only publishes UI state after the save succeeds. A storage notification refreshes other open tabs.

`crates/server` is an Axum API. Staff bearer credentials map to exactly one tenant and role; request JSON cannot select either. Each server command loads current tenant state inside a SQLite transaction, runs the same Rust engine and commits once. The initial implementation stores each tenant aggregate as JSON to keep the pilot small and transactional. It is suitable for a bounded pilot, not large-scale multi-restaurant SaaS. Migrate to normalized records and pagination before high volume.

Guest access uses a random active-visit bearer token generated by the server. Guest responses expose only that visit’s orders and bill, with no previous visit, staff audit, payments list or session tokens. Guest commands are restricted to order submission and service requests. A photo of the current visit QR grants access to that visit; physical seating validation and QR rotation during a live visit are future work. No guest identity is claimed.

Order states: pending → accepted → preparing → ready → served; pending → rejected. Individual lines progress queued → preparing → ready → served. Staff orders start accepted. Payment is separate. A session can close only once every order is served/rejected and balance is zero; then its table requires cleaning and its token stops working.

An order snapshots trusted menu names and prices at submission. Approving a pending order confirms that snapshot; later edits do not rewrite existing order prices. Availability is rechecked on approval. Billing rates cannot change with any active visit, preventing retroactive changes. This release deliberately has no in-flight amendments or refunds.

Order and payment retry keys are scoped to the visit. Repeat submissions return existing state without a second record. The API serializes all writes; local writes serialize across tabs. Failed actions never partially mutate durable data. Successful changes append an audit event. It is not tamper-proof accounting storage; local demo data is user-editable.

The default local demo can be tested without servers. The API is separately opt-in; unavailability never silently falls back to local writes. Remote staff polling refreshes every five seconds. Online payment is unimplemented and cannot reduce balance.
